# L1-UX08 — Unified Activity Center & Source Recovery

## Goal
Turn existing multipart/retry state plus durable Compute job state into a coherent cross-page beta-minimum activity experience, and make `选择原文件继续` a true fallback rather than the default resume path.

Under `GOAL-BETA-PREP01` this card is authorized only after Compute production cutover and RF-SEARCH01 production closure are green. Keep the implementation deliberately small enough for internal-beta readiness.

## Scope

### Global Activity Center — beta v0.1

Persistent cross-page activity surface, desktop bottom-right and responsive/mobile equivalent.

#### Upload
- immediate feedback after drag/drop or file selection;
- human states for queued, preparing/checksum, reserving, uploading, paused/resumable where already supported, completing/verifying, complete and failed;
- file-level progress, uploaded/total bytes, speed and ETA only where already reliable;
- multi-file aggregate state only if it falls out of the existing transfer model without broad new architecture;
- pause/resume/retry/abandon only through existing safe upload contracts;
- completed rows remain briefly visible before quiet dismissal.

#### Metadata / Compute
- show only durable `queued | processing | succeeded | failed` user states backed by Job Core;
- state survives reload because the server job is authoritative;
- no per-page OCR progress, raw OCR text, worker internals, GitHub terminology, capability/source URL, or candidate payload appears in the activity surface;
- activity may link back to the existing resource/details review flow rather than creating a new metadata workspace.

#### Download
- show only reliably observable states such as `preparing | started | failed`;
- do not proxy large file bytes through Core merely to fabricate percent progress;
- do not claim byte-level progress when browser-direct OSS/Range download does not expose a trustworthy measurement.

### Source Recovery
Use progressive enhancement:

1. same browser session: reuse the existing in-memory `File` automatically;
2. supported browsers: retain a `FileSystemFileHandle` in IndexedDB after an explicit user-granted selection/drag capability where available, then query/request permission and `getFile()` on resume;
3. only when automatic source access is unavailable/denied/stale, show `选择原文件继续`.

Before reusing old multipart parts, revalidate source identity against server-authoritative pending upload identity. Filename/size alone are insufficient; checksum mismatch must fail closed.

### Product distinction

`Activity Center` is live/current operational activity. `待处理` remains durable recovery state for unfinished uploads/resources. Do not merge those concepts into one ambiguous queue.

## Non-goals
- no upload protocol rewrite;
- no schema migration unless proven unavoidable and separately reconciled inside GOAL-BETA-PREP01;
- no service worker/background-sync requirement;
- no path-string persistence or attempt to bypass browser file permissions;
- unsupported browsers retain current safe manual-source fallback;
- no OSS/provider changes;
- no full task history, advanced filters, search/filtering of activities, general notification platform, polished animation program, complex pause scheduler, per-page OCR telemetry, RAG/indexing states, or unrelated UI redesign;
- no download proxy through Core solely for progress reporting.

## Acceptance
- drag/select shows activity immediately;
- same-session interruption can resume without reopening a file picker;
- supported persisted-handle path resumes after reload when browser permission allows;
- permission loss/deleted/moved/changed file produces a clear fallback;
- wrong source file cannot append to prior multipart data;
- Activity Center and `待处理` have distinct roles: live activity vs durable recovery state;
- Metadata Suggestion queued/processing/succeeded/failed is visible and reload-safe through Job Core;
- download preparing/started/failed is shown only when actually observable;
- browser tests cover supported/fallback behavior with capability mocks plus one real-browser journey;
- QA-GOLDEN01 can consume this surface in the final beta gate.

## Completed
- Replaced the page-flow upload queue with one responsive global Activity
  Center that composes live upload, durable Metadata Suggestion, and observable
  download states.
- Preserved reliable upload progress/bytes/speed/ETA and existing bounded
  pause/retry/abandon contracts; completed uploads remain briefly dismissible.
- Recovered Metadata Suggestion activities from the existing server-authorized
  per-resource Job Core endpoint and polls only queued/running jobs. The surface
  exposes no worker/provider/source/capability/candidate internals.
- Added download preparing/started/failed without proxying bytes or inventing
  byte progress.
- Added same-session automatic File reuse plus optional user-granted
  `FileSystemFileHandle` retention in IndexedDB. Permission loss, stale handles,
  and checksum mismatch fail closed to the manual original-file fallback;
  paths and file contents are never persisted.
- Added capability/storage/fallback/reload/download/mobile contract coverage.
- Real-browser pre-acceptance found that an embedded browser can expose the
  enhanced file-picker API while leaving its promise permanently pending. The
  upload command now preserves the handle-capable path while immediately
  exposing an explicit standards-based file-selection fallback instead of
  leaving the user with a no-op.
- Real-browser pause/resume evidence proved Core status/part-authorization
  responses stayed 200 and OSS/CORS/credential boundaries were unchanged, but
  a multipart retry remained `queued` during its first status request. The
  scheduler consequently started the same retry on intervening renders. The
  retry now claims an active phase before any I/O, with a regression test that
  holds the status request pending across navigation and proves exactly one
  workflow starts.
- The first real Metadata Suggestion worker run passed bounded OCR and the
  GitHub-hosted memory contract (peak Node RSS 533,209,088 bytes; GNU time
  maximum RSS 521,600 KiB) but its final Core result transaction returned 500
  and rolled back with the job still running. The worker now retries transient
  result callbacks within a fixed bound and, after exhausted success-result
  retries, best-effort terminates the exact job as `compute_internal_error`
  through the same capability instead of stranding it until the two-hour
  deadline. Core adds only safe error type/SQLite code/source-frame evidence;
  no candidate text, source/callback URL, or capability is logged.
- The replacement-release browser journey exposed one real completion-path
  defect: a canonical-library UNIQUE filename collision (`files.owner_domain_id,
  files.display_name`) surfaces only at the final promotion transaction, so the
  whole upload completes physically while logical activation rolls back. The
  multipart stayed `completing`, `POST multipart/complete` returned a generic
  409 `invalid_state`, and `GET status` leaked a raw `SqliteError`/500. The
  bounded repair (no schema change): the canonical default-upload creation now
  rejects a duplicate holding name with `name_conflict` before any bytes are
  uploaded; the completion/status wrappers map the promotion-time unique
  collision specifically to `name_conflict` (status never leaks a raw
  SqliteError); abandoning a physically-completed-but-logically-pending upload
  discards the matching orphan object; and repeated completion attempts fail
  stably without state thrash. Regressions cover the early rejection, the clean
  status mapping, the no-thrash repeat, and the orphan-object discard.
  Production-side run-owned fixtures from the interrupted attempts were fully
  recovered (server-authoritative status finalize after the name conflict
  cleared) and purged with zero residue; the pre-existing durable pending
  fixtures were never touched.
