## Task ID

L1-E03 — Authentication & Authorization

## Goal

Establish secure account authentication, persistent opaque sessions, reusable protected-route authorization, and server-derived account identity within the approved lightweight architecture.

## Scope

- measured Argon2id password hashing with bounded concurrency for the 512 MB server
- SQLite session schema, repository contract, and implementation
- cryptographically random opaque session tokens with only token digests stored at rest
- authentication service for login, session resolution, logout/revocation, and expiry
- same-origin CSRF enforcement and secure cookie policy
- login throttling suitable for the single-process deployment
- login, logout, and current-session API routes with validated input
- reusable Fastify authentication guard exposing server-derived account context
- application composition, local configuration, tests, and concise API/development documentation

## Non-goals

- public registration, password reset, email verification, MFA, roles, or administration UI
- drive/file-management routes or ownership decisions beyond reusable authenticated account context
- OSS integration, uploads, downloads, or frontend file-browser functionality
- Redis, JWT, external identity providers, or additional resident services
- production TLS/Nginx/systemd configuration
- Layer 2 or Layer 3 features

## Acceptance Criteria

- [x] a maintained Argon2id package and concrete parameters are measured and recorded for Node.js 24 and the 512 MB constraint
- [x] password hashing/verification concurrency is bounded without weakening the selected parameters
- [x] opaque session secrets have at least 256 bits of entropy and only SHA-256 digests are persisted
- [x] SQLite-backed sessions survive application restarts and support expiry and revocation
- [x] session cookies are `HttpOnly`, `SameSite=Strict`, scoped, bounded, and `Secure` in production
- [x] unsafe `/api` requests enforce an exact allowed origin and login attempts are throttled
- [x] login/logout/current-session routes validate input and return generic authentication failures without leaking secrets
- [x] a reusable guard supplies account identity from the session rather than client-provided ownership data
- [x] integration tests cover success, failure, disabled accounts, expiry, revocation, cookie policy, CSRF, rate limiting, restart persistence, and protected-route behavior
- [x] tests, type-checks, builds, dependency audit, and a local password benchmark pass
- [x] no OSS, file-management, or frontend feature scope is introduced
