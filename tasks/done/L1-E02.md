## Task ID

L1-E02 — Database Foundation

## Goal

Establish the approved SQLite persistence foundation for account, folder, and file metadata while keeping business modules independent of SQLite APIs.

## Scope

- SQLite connection lifecycle and safety pragmas behind the persistence boundary
- ordered, checksummed, atomic SQL migrations and a migration command
- account/user representation and repository interface
- folder hierarchy representation and repository interface
- logical file/storage metadata representation and repository interface
- SQLite repository implementations and explicit transaction boundary
- database integrity and repository integration tests
- local database configuration and migration documentation

## Non-goals

- login, logout, sessions, password hashing, or HTTP authentication routes
- folder/file service behavior or HTTP APIs
- OSS SDK usage, upload authorization, downloads, or physical deletion
- frontend database features
- production deployment or backup automation
- Layer 2 or Layer 3 features

## Acceptance Criteria

- [x] `better-sqlite3` is confined to the SQLite persistence adapter
- [x] migrations are ordered, checksummed, atomic, repeatable, and runnable from npm
- [x] the initial schema represents accounts, folder hierarchy, and complete logical file/storage metadata
- [x] foreign keys and checks prevent cross-owner folder/file references and invalid lifecycle metadata
- [x] repository interfaces are owned by the relevant business modules and have SQLite implementations
- [x] an explicit transaction boundary rolls back failed multi-repository work
- [x] tests, type-checks, builds, migration smoke checks, and dependency audit pass
- [x] no authentication flow, OSS integration, or file-management API is introduced
