# L1-UX06 — Canonical Catalogue Presentation Repair

## Task ID
L1-UX06 — Canonical Catalogue Presentation Repair

## Goal
Repair the post-PROD-06A Library catalogue so the canonical shared corpus reads as one coherent scholarly catalogue rather than a stacked Shared-Library panel plus legacy Drive table.

## Scope
- Render one unified catalogue/list surface for canonical Library holdings and Owner-managed folders; do not stack a separate holdings feed above the legacy table.
- Keep column/header placement coherent at the top of the catalogue on desktop; preserve responsive/mobile behavior.
- Reuse the existing file-type badge/icon system for PDF, image, text, and generic files.
- Remove redundant descriptive copy such as `当前账户可访问的共享学术资料。` under the Library heading.
- Do not repeat a `recordLabel` when it is merely the migrated/original filename; the compact row should prefer one human-facing resource title plus useful size/state only.
- Preserve Preview, Download, Favorites and accessible row actions.
- Provide Owner/Manager access to the normal recoverable shared-resource lifecycle (`移入回收站`) through an authority-correct Library-owned path; Members must not receive destructive corpus authority.
- Keep original filenames, object keys, stable IDs, checksums, provenance, Scholarly Record/Artifact/Version lineage, and Personal Research Overlay unchanged.

## Non-goals
- No permanent deletion / `PROD-03C2`.
- No canonical metadata schema, automatic title extraction, OCR, full-text search, embeddings, RAG, or external catalogue lookup.
- No production deployment, production contact, or production cleanup in this repository task.
- No broad visual redesign unrelated to the concrete catalogue regressions found in Owner first-use review.
- Do not begin `RF-META01`, `RF-METASUGGEST01`, or `RF-SEARCH01` inside this card.

## Acceptance Criteria
- Root `资料库` presents one catalogue hierarchy; there is no visually separate holdings list followed by a second Name/Size/Updated table.
- Desktop headers align with the rows they describe and remain above those rows.
- PDF/image/text/generic type icons are present in the canonical catalogue using the established icon semantics.
- The redundant canonical-summary sentence is absent.
- A migrated holding does not show the same filename twice merely because `recordLabel === file.displayName` or is equivalent migrated residue.
- Preview/download/favorite behavior remains green.
- Owner/Manager can move an eligible Library-owned resource to the recoverable recycle lifecycle, retrieve it in the normal Recycle experience, and restore it through server-authorized Library governance; Members cannot list or restore Library governance entries.
- No CAS/revision, ownership-domain, provenance, private-overlay, or stable-object invariant is weakened.
- Verification is focused and proportionate: affected frontend/component tests plus focused backend lifecycle/authorization tests when the Library-owned recycle path changes; no replay of historical production campaigns.

Diagnosis recorded before code changes:
- Root `DriveView` renders `SharedLibraryPanel` before the later Owner-only `EntryTable`; the holdings feed and the Name/Size/Updated table are therefore two independent structures, and the only desktop header necessarily appears below the holdings.
- The existing `EntryTable`, `FileBadge`, `RowMenu`, `StarButton`, Preview dialog, and responsive `.entry-table` / `.entry-row` CSS already provide the required catalogue semantics and should be extended/reused instead of creating a third listing system.
- `api.deleteFile(fileId)` / `DriveService.deleteFile(accountId, fileId)` deliberately resolve only the authenticated account ownership domain. An admitted canonical holding belongs to the Library ownership domain, so routing it through the account path would fail or confuse authority with contributor provenance.
- The smallest authority-correct lifecycle contract is a narrow Library HTTP action: require an effective active manager, resolve the holding inside the exact Library, resolve its active file inside that Library's ownership domain, compare the established opaque drive-entry version, and atomically create the normal recycle group plus CAS-guarded deleted-state transition with the initiating account retained as audit/provenance. Members, wrong Libraries, and guessed file IDs retain the same non-disclosing not-found result.
- `LibraryHoldingView` currently lacks enough mutable-state evidence for safe lifecycle mutation. It must expose the minimum opaque `driveEntryVersion` token (and ordinary updated timestamp for the catalogue column), while continuing to omit object keys, checksums, uploader identity, and private-overlay data.
