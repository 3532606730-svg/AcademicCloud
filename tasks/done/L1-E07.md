## Task ID

L1-E07 — Security & Reliability

## Goal

Harden the completed Layer 1 application against common HTTP/security failures and make metadata/object lifecycle inconsistencies observable and conservatively recoverable without adding infrastructure services.

## Scope

- production-safe HTTP security headers, bounded request behavior, and secret-safe structured logging
- audit events for authentication/authorization failures and destructive file lifecycle operations without logging credentials, cookies, signed URLs, or object keys
- repeatable authorization/input/error regression coverage across the completed API
- bounded expired-session cleanup that is not required for authorization correctness
- a conservative, explicit maintenance boundary for inspecting and reconciling abandoned pending uploads and interrupted purges
- checksum/upload/delete invariants, restart behavior, fault injection, and operational reliability documentation
- configuration validation appropriate to the single-process 512 MB target

## Non-goals

- real credentials, live OSS calls, bucket/RAM/CORS changes, production deployment, TLS certificate issuance, or server mutation
- backup/restore execution, Nginx/systemd installation, release packaging, or representative live-file acceptance (L1-E08)
- Redis, queues, schedulers, permanent workers, multiple application instances, recursive folder deletion, or automatic destructive object cleanup
- antivirus scanning, DLP, enterprise audit administration, sharing, or any Layer 2/3 capability

## Acceptance Criteria

- [x] API responses carry a documented secure header baseline without breaking private signed-object access
- [x] structured logs redact cookies, authorization, password-bearing request data, signed URLs, upload policy/signature fields, and provider secrets
- [x] authentication/origin/authorization and destructive lifecycle outcomes emit useful stable audit events containing only server-derived identifiers
- [x] request, upload, KDF, storage, and maintenance concurrency/time bounds remain explicit and compatible with the 512 MB target
- [x] expired sessions can be pruned safely and repeatably without weakening per-request expiry/revocation checks
- [x] stale pending/purging records can be inspected and reconciled only through conservative expected-state transitions; ambiguous/mismatched/provider-failure states preserve data and metadata
- [x] no maintenance path silently overwrites or deletes an ambiguous object, trusts client ownership, or exposes provider details
- [x] deterministic tests cover security headers/redaction, authorization matrices, restart/fault cases, pending reconciliation, and interrupted deletion recovery
- [x] reliability/security operations and residual risks are documented for L1-E08 deployment consumption
- [x] repository tests, type-checks, production builds, audit, migration/integrity checks, and diff review pass
