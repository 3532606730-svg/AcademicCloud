# ADR-043 — Document source generations and physical-page locations

Date: 2026-09-15
Status: Accepted for local implementation under the reassessment charter; production migration awaits the final combined release

Files have a mutable revision used for concurrency control. Rename, move, recycle and other metadata operations can advance it. The existing Catalog source fingerprint deliberately includes that revision and must remain unchanged. Scholarly ArtifactVersion currently references a file without capturing immutable byte identity. Neither identifier is a durable page-note attachment on its own.

Add an append-only document source registry in Core Drive. A source records its file ID, storage provider, object key, byte count, checksum algorithm/value and observation timestamp; a separate current-source relation references the same file/source pair. The public descriptor contains only resourceId (the existing file ID) and sourceId. IDs are identifiers, never capabilities or a substitute for source authorization. There is no global checksum lookup or disclosure of storage keys in this descriptor.

Migration037 backfills activated files from their already recorded metadata, including recoverable/deleted historical files. This does not re-read objects, invent a new checksum, claim fresh integrity verification or copy bytes. Pending uploads have no source generation. Ordinary SQLite triggers create a generation atomically when a file first activates or its recorded byte-identity tuple changes. Renames, folder moves, account-to-Library promotion, canonical editing and recycle/restore do not create a new generation. Returning to a previously seen byte tuple still creates a new generation; authored notes never reattach automatically.

Capture belongs at the database write boundary rather than two separate upload call sites. It therefore covers single and multipart activation, authorized maintenance and compatible older application writes during rollback. The triggers use standard SQLite only; they add no OCR/AI dependency, service or provider coupling. Immutable rows cannot be edited/deleted and composite foreign keys prohibit attaching a source to another file. A current-source relation must match the file's recorded byte tuple.

The existing authorized Preview/download response carries the descriptor, avoiding an extra browser request. Authorization checks happen before source disclosure. Bind the descriptor to the file snapshot used to sign the URL; if that source changes or becomes unavailable while storage authorization is in flight, fail with the existing concurrent-change behavior rather than label a different source with the old context.

DocumentLocation is resourceId + sourceId + a one-based physical PDF page number. Printed pages, leaves, volumes and citation locators are different concepts. Compute evidence uses its existing zero-based page indices and requires explicit conversion at a future adapter boundary. The current cross-origin native PDF iframe cannot reliably report the selected physical page. Initial page notes must ask for an explicit physical page; automatic progress must wait for a controlled Reader. No fabricated page count or observed reading position is stored.

Personal reading state and notes remain authored per-account overlays under ADR-014. Shared source authority does not expose another account's content, existence, counts or exports, including to the Owner. Recycle or lost resource access does not destroy authored notes; linked content becomes unavailable. Replacement keeps old-source notes distinct. Collections organize resources semantically and do not copy bytes or become storage folders. These overlay tables and product flows are separate from this Core identity migration.

Verification must cover migration/backfill/restart, immutable and cross-file constraints, single/multipart activation, changed bytes versus metadata-only changes, ownership promotion, failed transactions, source changes while signing, and non-disclosure to unauthorized callers. Catalog fingerprint/CAS behavior stays unchanged.

Rollback is additive: preserve the registry and migration ledger; never down-migrate or discard authored overlays to run an older binary. Startup enforces complete migration history, so an older binary must be paired with the full already-applied migration/admission directories and verified offline against the migrated schema before selection. An old release's incomplete migration directory must fail closed. Database triggers continue capturing activated/new byte generations even if older code omits the public descriptor. Final deployment requires the existing evidence-gated migration and recovery procedure once, after the integrated batch is ready.
