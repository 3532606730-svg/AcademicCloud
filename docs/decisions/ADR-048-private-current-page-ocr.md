# ADR-048 — Scenario-based OCR execution and private current-page results

Date: 2026-09-28; updated 2026-10-01. Status: Accepted member-owned connection, tutorial and isolation boundaries; PP-OCRv6 selected as the first online adapter for ordinary printed Chinese book pages. Connection profiles, persistence schema and product enablement remain open.

## Decision and sequencing

The Owner requested current-page OCR and full-book feasibility/accuracy assessment, then clarified that members should use their own devices for local OCR and asked to evaluate online OCR first. The subsequent Owner choice is a common connection interface through which members attach their own online or offline engine. The connection dialog must include simple, actionable tutorials for both paths. Online provider evaluation precedes preset selection. The earlier uncommitted proposal routing every member request through the Owner Local Pull queue is superseded. Whole-book evaluation does not authorize its product rollout, indexing, embeddings or RAG. The Owner accepts reasonably priced OCR and chooses to assess quality before setting a budget; no proposed numerical cap has been accepted. This exception concerns OCR usage only. Zero additional infrastructure/billable GitHub and coordinated-release constraints remain.

The Owner's later preference is to use an already installed qualified engine on the requesting member's own device first. The member may explicitly download a suitable engine/model; installation alone does not establish language/layout suitability or accuracy. When local hardware or language/layout support is insufficient, the member may explicitly connect their own online OCR account, including an engine offering positions. Member work never silently falls back to Owner compute, credentials or quota, and a local request never silently switches to cloud processing. Tutorials should explain the local and online choices in ordinary language.

Current-page results bind to the actually rendered one-based physical page and immutable resourceId/sourceId. They are unverified machine text, initially account-private, not canonical bibliography, private authored notes or a shared research-activity feed. Source access and generation must be checked on every protected read/write. Page/document/source changes reject late results from the previous selection. A high engine confidence never means human verification. Client-produced results remain explicitly untrusted and cannot confer canonical authority.

## Execution locations

October1 model selection: the Owner requested the most suitable model for book intake before proceeding with integration. Select Baidu PP-OCRv6 as the first online adapter for ordinary printed Chinese title/copyright/body pages. The completed fixed sample has Chinese CER27/1910=1.4136% versus VL129/1910=6.7539%; this supports a scenario-specific choice, not a universal or whole-book accuracy claim. VL remains a later English-body candidate; handwritten pages, vertical ancient books and traditional Mongolian require separate qualification. A qualified engine already installed on the requesting member's own device remains preferred; the cloud trial does not qualify local PP-OCRv6_small weights.

The first adapter accepts one bounded, already-rendered static PNG (non-interlaced, non-indexed, at most8-bit channels and a restricted ancillary subset) and calls the fixed PP-OCRv6 endpoint once, with member access-token resolution injected at construction. Validate chunk CRCs, bounded exact scanlines and actual decode before obtaining credentials or submitting. No complete-PDF URL, automatic retry, environment credential fallback or Owner dispatch is introduced. Keep document rotation/unwarping disabled so optional line boxes remain in the submitted-image coordinate frame. Preserve line order, low-confidence text and explicit truncation. The API reports per-line scores, so page confidence is null rather than an invented aggregate. The provider does not disclose exact weights, so modelVersion remains null. OCR machine text does not replace bibliographic evidence validation or canonical CAS.

This is an internal implementation step. The unchanged deferred HTTP interface, member credential storage, tutorials, source/private-result lifecycle and normal signed-in Reader acceptance still gate product activation. No schema migration or runtime change is needed for the unconnected adapter; rollback removes its unused module. Future private result/profile persistence requires its own lifecycle and rollback decision. Official API shape and limits were rechecked on October1: [PP-OCRv6](https://cloud.baidu.com/doc/OCR/s/6mncwkr9c).

- Online OCR is a candidate for current pages and limited bibliographic evidence. Each member configures their own provider account; fees and quota belong to that account. Evaluate official APIs, cost controls, supported scripts/layout, data handling and measured quality before activation. Stored credentials must be account-private, encrypted and revocable, never returned to other clients or exposed in logs/URLs; Core remains an authorization/control plane rather than an OCR model host.
- Member local OCR runs on that member's device using a qualified installed engine or one the member explicitly downloads. Prefer an account-paired connector that initiates outbound communication and may receive only its account's currently authorized OCR tasks; it gains no catalogue administration or cross-account authority. A browser-local adapter is another possible implementation. This checkpoint does not add an installer, pairing API or native service. Online failure, quota exhaustion or missing credentials never silently dispatches member research work to the Owner machine.
- Existing Owner-operated automatic bibliographic Local Compute remains unchanged. Reuse of private Reader OCR in shared cataloguing is not implicit: candidate provenance, evidence validation, current source authority and canonical CAS still govern that separate path.
- Whole-book execution may eventually use a document-aware cloud model or a qualified local specialist. Number of pages alone does not justify custom training. Training material, script inventory, segmentation, blind validation and exact checkpoint identity determine suitability.

## Authorization, cost and source disclosure

The initial interface checkpoint performed public-documentation review and local reference preparation. The Owner subsequently authorized bounded OCR integration and a real trial using free quota first, completed the OCR agreement and authorized the existing restricted Baidu trial app to process eight frozen pages from four real books. PP-OCRv6 and PaddleOCR-VL each receive one pilot page first, followed by the remaining seven, with at most eight submissions per engine and no blind retries. Verify the selected account's actual remaining free quota and billing state before dispatch. Purchasing a package, enabling postpaid billing and paid fallback are outside this trial; no future recurring numerical budget has been selected.

The existing account/app, engines and fixed source-page scope do not require repeated authorization. Reuse the recorded consent and verified unchanged trial tooling while satisfying the quota/billing checks. New sources or providers, broader credential permissions, or paid activation require a separately defined scope. Login/session restoration and fresh factual checks within the existing scope do not reopen the source-disclosure decision. Trial outcomes must be recorded from execution evidence; authorization alone establishes no result or accuracy claim.

Free quotas are not perpetual capacity. Members using different provider accounts have separate quota and charges; any intentional sharing must be explicit. Future use must verify the selected account billing state and user-selected cost controls, including ambiguous retries. An explicit spending limit must stop new dispatch, not merely display an alert. The immediate free-only trial does not reverse the accepted possibility of reasonable OCR fees after quality evaluation.

An online current-page request should disclose only the selected page image where practical. Passing a complete PDF URL with a page-number parameter grants access to the whole source and must be assessed as such. Provider retention claims apply only to the documented service; signed-result URL expiry does not establish content deletion or a no-training policy.

## Present implementation and compatibility

The existing HTTP reader-ocr.v1 interface remains deferred. A separate internal adapter contract provides common capabilities, one page image, cancellation and bounded machine results for future online/local implementations. It is not a universal vendor HTTP protocol or a production connection endpoint. Custom engines need an adapter; Core must not become an arbitrary user-URL proxy. No new HTTP route, persistence schema or worker dispatch is enabled. The unused Local Pull reader-job contract, server queue and client-cache migration drafts are hash-verified in ignored local candidate archives and removed from active source. In particular, migration040 is not admitted or executed.

The retained standalone explicit-page inspector and opt-in Paddle readerMode are local qualification primitives. They always render the selected page, retain low-confidence text, signal truncation and reuse existing bounded source/render/time handling. Existing bibliographic callers do not opt into readerMode. These helpers do not constitute Reader product delivery or a provider choice. The qualification caller must close its adapter in finally; aborting cold-start waiting alone does not terminate the warm process. A future Local Compute release must explicitly include and verify the changed Python sidecar: the current assembly copies the pinned runtime and does not automatically substitute the candidate sidecar.

September29 adds separately opt-in local line positions, not a connection transport or Reader overlay. Recognition-aligned rectangles carry final-text UTF-16 offsets and normalized image coordinates, with a512-box cap and explicit unavailable/invalid/limited states. Actual bitmap/viewport dimensions and PDF render transform preserve the coordinate frame. Invalid optional layout does not discard useful text; normalization or truncation must not attach a box to the wrong characters. Default bibliographic requests remain unchanged. Independent Astra ultra review of exact f3bb2b537c6f53b886d670c1bff77eb81992e2da is now complete and passes, alongside the recorded44 TypeScript and7 Python synthetic checks plus Compute types/build. The reviewer inspected source and supplied verification evidence without rerunning those tests. Real GPU page/layout qualification, Reader UI integration and production deployment remain unverified.

A later implementation decision must specify private result lifecycle, quotas, idempotency/CAS, source revocation, provider identity, failure recovery and compatible migration/rollback. Do not infer the former draft's queue, retention numbers or schema from this accepted boundary decision.

No real cloud call or Reader/product connector is added by these checks. These checks validate interfaces, not live vendor or product acceptance.
