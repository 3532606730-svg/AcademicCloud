# ADR-048 — Scenario-based OCR execution and private current-page results

Date: 2026-09-28. Status: Accepted member-owned connection, tutorial and isolation boundaries; provider, persistence schema and enablement decision remain open.

## Decision and sequencing

The Owner requested current-page OCR and full-book feasibility/accuracy assessment, then clarified that members should use their own devices for local OCR and asked to evaluate online OCR first. The subsequent Owner choice is a common connection interface through which members attach their own online or offline engine. The connection dialog must include simple, actionable tutorials for both paths. Online provider evaluation precedes preset selection. The earlier uncommitted proposal routing every member request through the Owner Local Pull queue is superseded. Whole-book evaluation does not authorize its product rollout, indexing, embeddings or RAG. The Owner accepts reasonably priced OCR and chooses to assess quality before setting a budget; no proposed numerical cap has been accepted. This exception concerns OCR usage only. Zero additional infrastructure/billable GitHub and coordinated-release constraints remain.

Current-page results bind to the actually rendered one-based physical page and immutable resourceId/sourceId. They are unverified machine text, initially account-private, not canonical bibliography, private authored notes or a shared research-activity feed. Source access and generation must be checked on every protected read/write. Page/document/source changes reject late results from the previous selection. A high engine confidence never means human verification. Client-produced results remain explicitly untrusted and cannot confer canonical authority.

## Execution locations

- Online OCR is a candidate for current pages and limited bibliographic evidence. Each member configures their own provider account; fees and quota belong to that account. Evaluate official APIs, cost controls, supported scripts/layout, data handling and measured quality before activation. Stored credentials must be account-private, encrypted and revocable, never returned to other clients or exposed in logs/URLs; Core remains an authorization/control plane rather than an OCR model host.
- Member local OCR runs on that member's device after explicit model/engine download. Prefer an account-paired connector that initiates outbound communication and may receive only its account's currently authorized OCR tasks; it gains no catalogue administration or cross-account authority. A browser-local adapter is another possible implementation. This checkpoint does not add an installer, pairing API or native service. Online failure, quota exhaustion or missing credentials never silently dispatches member research work to the Owner machine.
- Existing Owner-operated automatic bibliographic Local Compute remains unchanged. Reuse of private Reader OCR in shared cataloguing is not implicit: candidate provenance, evidence validation, current source authority and canonical CAS still govern that separate path.
- Whole-book execution may eventually use a document-aware cloud model or a qualified local specialist. Number of pages alone does not justify custom training. Training material, script inventory, segmentation, blind validation and exact checkpoint identity determine suitability.

## Authorization, cost and source disclosure

This checkpoint performs public-documentation review and local reference preparation, not external inference. It does not open accounts, create credentials, activate billing or send academic source bytes to third parties. Free quotas are not perpetual capacity. Members using different provider accounts have separate quota and charges; any intentional sharing must be explicit. Future use must verify the selected account billing state and user-selected cost controls, including ambiguous retries. An explicit spending limit must stop new dispatch, not merely display an alert. No limit has been chosen for the Owner assessment yet.

An online current-page request should disclose only the selected page image where practical. Passing a complete PDF URL with a page-number parameter grants access to the whole source and must be assessed as such. Provider retention claims apply only to the documented service; signed-result URL expiry does not establish content deletion or a no-training policy.

## Present implementation and compatibility

The existing HTTP reader-ocr.v1 interface remains deferred. A separate internal adapter contract provides common capabilities, one page image, cancellation and bounded machine results for future online/local implementations. It is not a universal vendor HTTP protocol or a production connection endpoint. Custom engines need an adapter; Core must not become an arbitrary user-URL proxy. No new HTTP route, persistence schema or worker dispatch is enabled. The unused Local Pull reader-job contract, server queue and client-cache migration drafts are hash-verified in ignored local candidate archives and removed from active source. In particular, migration040 is not admitted or executed.

The retained standalone explicit-page inspector and opt-in Paddle readerMode are local qualification primitives. They always render the selected page, retain low-confidence text, signal truncation and reuse existing bounded source/render/time handling. Existing bibliographic callers do not opt into readerMode. These helpers do not constitute Reader product delivery or a provider choice. The qualification caller must close its adapter in finally; aborting cold-start waiting alone does not terminate the warm process. A future Local Compute release must explicitly include and verify the changed Python sidecar: the current assembly copies the pinned runtime and does not automatically substitute the candidate sidecar.

A later implementation decision must specify private result lifecycle, quotas, idempotency/CAS, source revocation, provider identity, failure recovery and compatible migration/rollback. Do not infer the former draft's queue, retention numbers or schema from this accepted boundary decision.

## Evidence and next gate

The unconnected Compute changes pass35 scoped tests and typechecks with independent review. The internal engine contract adds11 boundary tests; the complete contract package passes14 tests, typecheck and build. This is interface validation, not live vendor or product acceptance. Four preserved Owner sources supplied eight rendered pages and 6,719 independently transcribed reference characters, frozen before any evaluated engine output. These are agent visual references with two uncertain characters, not human-certified gold. No OCR result or new accuracy percentage has been measured on that sample.

See [online provider assessment and dialog tutorial requirements](../evaluation/online-ocr-options.md) and [current-page/full-book qualification](../evaluation/current-page-and-book-ocr.md). Tutorial acceptance includes actual provider-specific steps, a real connection/capability test that never sends the current document (use a built-in synthetic image with any fee disclosed if the vendor lacks a capability probe), clear payer/data-location information, useful failure recovery, keyboard/focus behavior and mobile layout. Show no working download or connection control until its implementation exists. Next adapt the implemented internal contract to a chosen bounded evaluation and member-owned connection transport; actual activation must satisfy source-disclosure, account/cost, measured-quality and normal signed-in Reader acceptance gates. Budget remains effect-first as the Owner requested. No production release or main merge occurs in this checkpoint.
