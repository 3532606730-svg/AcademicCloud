# Object Storage Boundary

## Contract

Layer 1 business code depends on `StorageAdapter`. It does not import or expose the Alibaba Cloud OSS SDK. The contract has four capabilities:

- issue a short-lived browser-direct upload authorization for one exact object key, byte length, and MIME type;
- issue a short-lived signed GET URL for one exact object key and a safe response filename;
- read object size, ETag, provider checksum, MIME type, and modification time;
- delete one exact object key idempotently.

Object keys are generated by the application from 32 cryptographically random bytes. They have the form `objects/<two hex characters>/<62 hex characters>` and never contain a display filename, folder path, account identifier, or other client-controlled material. Display names remain logical database metadata.

`InMemoryStorageAdapter` implements the same contract for deterministic service and integration tests. It never performs network I/O.

## Alibaba Cloud OSS adapter

`AliyunOssStorageAdapter` confines OSS-specific policy fields, signing, response headers, and error handling to `backend/src/storage/aliyun/`. The `ali-oss` package is imported only by the client factory in that module.

Browser uploads use an expiring POST policy. Its signed conditions require:

- the one generated `key`;
- a content-length range whose lower and upper values both equal the declared byte length;
- the declared `Content-Type`;
- the browser-computed expected `Content-MD5`, so OSS rejects different bytes before storage;
- `x-oss-forbid-overwrite=true` so a still-valid authorization cannot replace the verified object;
- `success_action_status=201`;
- the configured private bucket;
- the security token when temporary credentials are configured.

The browser must submit every returned field unchanged. The file-management service creates pending database metadata, returns this authorization, and verifies provider metadata before activating the file.
The file-management service now stores the browser-computed expected MD5 before authorization and compares it with the provider-calculated `Content-MD5` returned by `HEAD`; the checksum is not treated as ETag. OSS ignores `x-oss-forbid-overwrite` for versioned buckets, so the Layer 1 bucket must have versioning neither enabled nor suspended.

Downloads use an SDK-generated V4 signed URL (`authorizationV4: true`). The signed response override supplies both a sanitized ASCII `filename` and an RFC 5987 UTF-8 `filename*`. The bucket remains private; no permanent public URL is returned.

`HEAD` metadata treats a provider 404 as an absent object. `DELETE` treats a provider 404 as success, making retry behavior idempotent. Other provider failures propagate to the caller so the file service can preserve database state and report a retryable failure. ETag is exposed separately because multipart-object ETags are not universally MD5 checksums. `Content-MD5` is preferred as the checksum when present, with OSS CRC64 as a fallback. SDK requests have an explicit 30-second default timeout, configurable from 1 to 120 seconds.

## Configuration

The adapter requires these server-side variables:

| Variable | Meaning |
| --- | --- |
| `OSS_ENDPOINT` | Exact OSS service origin; HTTPS is mandatory in production |
| `OSS_REGION` | Region identifier such as `oss-cn-hangzhou` |
| `OSS_BUCKET` | Private, DNS-compatible bucket name |
| `OSS_ACCESS_KEY_ID` | Server-side AccessKey or temporary credential ID |
| `OSS_ACCESS_KEY_SECRET` | Server-side secret; never sent to the browser or committed |
| `OSS_STS_TOKEN` | Optional temporary credential token |
| `OSS_UPLOAD_AUTHORIZATION_SECONDS` | POST policy lifetime, 30-900 seconds; default 300 |
| `OSS_DOWNLOAD_AUTHORIZATION_SECONDS` | signed GET lifetime, 30-900 seconds; default 300 |
| `OSS_REQUEST_TIMEOUT_MILLISECONDS` | SDK request timeout, 1,000-120,000 ms; default 30,000 |

Production deployment should use a narrowly scoped RAM identity limited to the configured bucket and application-generated object prefix. Credentials belong in the deployment secret store, not `.env.example`, logs, client bundles, database rows, or API responses. Bucket creation, CORS configuration, RAM policy changes, credential provisioning, and live network checks require a separately authorized deployment operation.
